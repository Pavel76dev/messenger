## 1. Git: что мы видим в Source Control

В панели **Source Control** (контроль версий) появляются файлы проекта, которые Git отслеживает.

**Вопрос преподавателя:** какие файлы мы здесь *не* видим?

**Ответ:** файлы и папки, перечисленные в **`.gitignore`**.

### Что такое `.gitignore`

Правила вида «игнорируй / не отслеживай». Git не показывает эти пути в списке изменений и не кладёт их в коммиты.

Типичные примеры в этом проекте:

| Что игнорируется | Зачем |
|------------------|--------|
| `.env` | Секреты: пароль БД, ключи приложения. В репозиторий не должны попадать. |
| `vendor/` | PHP-библиотеки (Composer). Их не правят вручную — ставят командой `composer install`. |
| `node_modules/` | JS-зависимости. Аналогично: ставят через `npm install`. |

**Идея:** в Git храним *наш* код и «слепок» проекта (миграции, сиды, конфиги без секретов), а не тысячи строк чужих библиотек. Библиотеки при необходимости ставятся заново по `composer.json` / `package.json`.

> Если репозиторий перенесли «без Git», его нужно снова инициализировать (`git init` / инициализация в IDE), иначе Source Control пустой или неполный.

## 2. Первый коммит

1. В Source Control нажать **Stage All Changes** (взять все изменения в индекс).  
   Можно стейджить не всё сразу, а частями — несколько коммитов подряд.
2. Написать сообщение коммита, например: `первый коммит` / `начало`.
3. Нажать **Commit**.
4. Пока **не публиковать** (не push), если так решили на занятии.

Проверка в терминале:

```bash
git log
```

Должен появиться первый коммит со всеми застейдженными файлами.

**Зачем это нужно:** дальше каждое изменение видно в Source Control (и в diff: зелёное — добавлено, красное — удалено). Можно понять, куда «ушла» правка агента/нейросети, и откатить лишнее.

## 4. Cursor и агенты (кратко с занятия)

- **Cursor** — среда разработки (похожа на VS Code), а не «одна нейросеть».  
  Внутри выбираются агенты/модели; есть подписка (на занятии упоминали ~$20 / месяц и Pro ~$60).
- Бесплатный лимит маленький; для серьёзной работы нужна подписка.
- «Безлимита» как такового почти нет: модели крутятся на дорогих GPU на серверах.
- Агент может задавать уточняющие вопросы по скоупу — на них нужно отвечать явно.

**Пример ответов агенту по этой задаче:**

1. Профиль: имя, email, пароль + фото.  
2. Вложения: любые файлы, несколько на одно сообщение.

Дальше агент составляет план (миграции, API, UI) и реализует по шагам. Имеет смысл **смотреть diff** и проверять руками — так же и учишься.

## 5. Что сделал агент (разбор результата)

### База данных

Связи в реляционной БД: не дублируем «Алиса/Боб» текстом в каждой строке, а храним **id**.

Пример логики сообщений:

- сообщение №1  
- относится к чату с `conversation_id = 1`  
- написал пользователь с `user_id = 2`  
- текст — в поле `body`

После фичи появляется таблица вложений, например **`message_attachments`**:

| Поле | Смысл |
|------|--------|
| `message_id` | К какому сообщению файл |
| `path` | Где лежит файл на диске |
| `original_name` | Имя файла у пользователя |
| `mime` | Тип (image/png, application/pdf, …) |
| `size` | Размер |

Таблица **`migrations`** помнит, какие миграции уже запускались, чтобы не создавать одно и то же дважды.

Также у пользователей появляется поле вроде **`avatar_path`** (путь к аватару).

### Backend (PHP / Laravel)

- Переработан контроллер сообщений: валидация не только `body`, но и файлов.  
- Сообщение можно отправить **с текстом и/или файлами** (лимиты на занятии: до 5 файлов, до 10 MB каждый).  
- Картинки в UI — с превью.  
- Отдельная логика профиля/аватара (обновление данных, загрузка/удаление фото).  
- Сериализация ответа API вынесена в единый метод (раньше поля собирали «вручную» массивом в нескольких местах).

### Frontend (JavaScript / React)

Приложение разделено:

- **Backend** — PHP (Laravel), API.  
- **Frontend** — JavaScript (React), UI.  
- Связь — через **API** (например `PATCH /api/me`, `POST /api/me/avatar`, multipart для сообщений с `files[]`).

Имеет смысл идти по шагам: сохранили в Git → следующее задание агенту → смотрите, что изменилось → пробуете в браузере.

### Файлы на диске

Файлы лежат в storage, наружу отдаются через symlink:

```bash
php artisan storage:link
```

Локально (OpenServer) это «как сервер, только локальный».  
Путь вида: `public/storage/attachments/1/<uuid>_name.png`.

На Linux-сервере symlink — обычная практика; хранение файлов устроено иначе, чем «просто папка как в Windows», но идея та же: публичный URL → реальное место на диске.

## 6. Проверка руками (как на занятии)

1. Открыть профиль → загрузить фото, при необходимости сменить email/пароль → сохранить.  
2. В шапке / у пользователя (например, Bob) появляется аватар.  
3. В чате приложить файл, написать текст (или только файл) → отправить.  
4. В ленте видно сообщение и вложение.  
5. В БД в `message_attachments` — запись с `path` на `attachments/...`.  
6. В проводнике — файл по этому пути под `storage` / `public/storage`.

## 7. Итоги занятия

- За короткое время (порядка часа) собрали заметную часть мессенджера «как у взрослых продуктов» — скорость сильно выше, чем «классическая» разработка 10 лет назад, особенно в связке человек + ИИ.  
- Важно не только «нажать Generate», а **понимать**, что сделано: Git, миграции, валидация, API, фронт/бэк, storage.  
- Учиться читать diff и задавать нейросетям точные вопросы; не тратить подписку впустую.  
- Автотесты (на занятии вскользь): прогон проверок перед запуском, чтобы не сломать ожидаемое поведение (грубый пример: у пользователя не должно быть двух одинаковых «портов»/конфликтующих правил — смысл в автоматической страховке).
