# PDR: Список задач из транскрипта

Product Design Record — решение «что строим» до детальной спеки.

## Проблема

После транскрибации аудио-клипа (014) пользователь получает сырой текст.
Если в речи был список дел, его приходится вручную разбирать. ИИ в проекте уже есть (012 / api-llm), но к транскриптам не подключён.

## Решение (одним абзацем)

По готовому транскрипту пользователь запускает извлечение задач: Laravel зовёт тот же `LlmClient` / api-llm, модель возвращает структурированный JSON; при наличии задач создаётся сущность «список задач», привязанная к этому аудио-клипу, и отображается **у этого клипа** в библиотеке. Если задач нет — список не создаётся, показывается понятное сообщение.

## Скоуп

### In

- Действие «Сделать список задач» у клипа со статусом транскрипта `done`
- Вызов существующего api-llm (не новый провайдер)
- Таблицы списка + пунктов; владелец = текущий пользователь; **`audio_clip_id` обязателен**
- UI: задачи видны **в карточке/строке соответствующего клипа** (library) — без отдельного глобального экрана «Мои задачи»
- Пункты: текст, порядок, статус `open|done` (переключение вручную)

### Out

- Отдельный раздел / кнопка composer «все задачи»
- Автозапуск LLM сразу после ASR без кнопки
- Извлечение из произвольных сообщений чата (не клипов) в v1
- Назначение исполнителей, дедлайны, приоритеты, подзадачи, проекты
- Шаринг списков в чат / группам
- Стриминг ответа LLM в UI
- Редактирование текста пунктов через LLM (только ручной toggle done / удаление списка)

## Пользовательские потоки

1. Библиотека → клип с готовым транскриптом → «Сделать список задач» → pending → под этим клипом появляются пункты **или** «задач не найдено».
2. В library у клипа раскрыть/увидеть связанные задачи → отметить пункт выполненным.
3. Повтор extract по тому же клипу → новый список под тем же клипом (история; старый не затирается).

## Решения и компромиссы

| Вопрос | Решение | Почему |
|--------|---------|--------|
| Где UI | Только у клипа в library | Явная связь «запись → дела»; меньше навигации |
| Триггер | Ручная кнопка | Контроль LLM; меньше ложных срабатываний |
| Модель ответа LLM | JSON `{ "title", "tasks": [ { "text" } ] }` / пустой `tasks` | Парсинг без эвристик |
| Где хранить | `task_lists` + `task_items`, FK на clip | Несколько списков с одного клипа |
| Фон | Не блокировать HTTP | LLM до десятков секунд |
| Пустой результат | Entity не создавать | Не засорять БД |
| Заголовок | LLM `title`, иначе короткий fallback | Удобно различать повторные extract |
| ADR | ADR-004; отдельный не нужен | Тот же `LlmClient` |

## Риски

- LLM вернёт не-JSON → ошибка на операции, клип/транскрипт не портить
- api-llm недоступен → как в 012
- Галлюцинации → system prompt: только явные поручения/пункты списка
